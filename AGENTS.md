# Working on this repository

- `spec/` is normative. Change the spec first, then the validator, then the tests. A rule's number never changes once published; new rules get new numbers.
- Backward compatibility is essential (claimset spec §2.6). The baseline is v0.39, set when the platform launched on 2026-11-09 (`BASELINE_VERSION` in `validate.py`; never changed). Every file valid under a version from the baseline stays valid under it for good: v0.39 and every later version change only by errata once a later version exists; before raising `SCHEMA_VERSION`, run `python3 tools/freeze_validator.py`; never change the rules of a frozen validator (`src/claimset/versions/`) or the files in `tests/compat/`. A new version may add optional fields and loosen rules; new required fields and stricter rules apply only to files of the new version. Bugs are fixed in every version they occur in, frozen ones included: in its validator (a crash, or a check that misreads what it checks) and in its specification text, listed under *Errata* in that version's file. A fix never makes a valid file invalid, and gets a test over every version (`tests/test_bugs.py`). `python3 tools/fuzz_types.py` finds where a validator fails on a value of the wrong type; run it after changing the validator. Lab records follow the same principle: a rule applies only to records begun under the version that introduced it.
- The package is the format, not a site. It defines the fields and what they mean, validates files, and gives the tools that write, check, package, migrate and submit claimsets. How a platform shows a claimset (pages, HTML, styles, the order and names of sections, panels, how scores look) and how it receives one (its API, MCP tools, uploads, consent) belong to that platform, in its own repository (EntryLib: github.com/entrylib/portal), never here. The specification says what a field means and how it is checked, not how it is displayed or sent; neither it nor the skills describe a platform's pages or routes beyond pointing to the platform's own description (EntryLib: https://entrylib.org/llms.txt). The plain-text reading view for models (spec Appendix D) is part of the format. The package holds no page view: the HTML that was here (`claimset render --html`) moved to the portal on 2026-11-12. What a platform needs to write values as the reading view does is `claimset.render`'s public helpers (`number`, `interval`, `uncertainty`, `value`, `statistic`, `statistic_note`, `DIGITS`); keep their names stable.
- The format is a core with extensions (spec §2.7). What only one kind of work needs goes in an extension (`spec/extensions/`, `src/claimset/extensions/`), never in the core; what two extensions would both define goes in the core. A released extension version's module is never edited: a new version is a new module.
- The claimset specification is the vocabulary of the lab record and the revision specification. A list, form or meaning they share with a claimset is defined once, in the claimset specification, and named there by section; in code it lives in `validate.py` and the lab imports it. Never copy one.
- The package uses only the Python standard library and supports Python 3.10+. Do not add dependencies without discussion.
- `skills/` bundles copies of the validator, specs and examples so each skill is self-contained, and `src/claimset/data/` carries copies of the specs, skill texts and the templates in `agents/`. Never edit those copies; edit the source and run `python3 tools/sync_skills.py`. `tests/test_sync.py` fails if they drift.
- Nothing in the tools, skills or specifications assumes one coding agent or one model provider. What differs between agents (where they read skills and instructions, their hooks, how they identify themselves, their sandboxes) is data in `src/claimset/agents.py`; `agents/` holds the one template `claimset init` writes for all of them.
- `README.md` is also the PyPI page, read by agents as much as people: keep it short, with full URLs, and put reference material in `docs/`. Its rules for agents are `agents/RULES.md`, copied verbatim (`tests/test_guide.py` checks it).
- Every validator rule needs a test: a valid case that passes and a broken case that fails with that rule's number.
- Run `python3 -m unittest discover -s tests` before committing.
- Specification text is written for LLM readers as much as for humans: plain, explicit, one meaning per term.

## Pull requests

- Keep the description short: a bulleted list of what was done, each item one or two sentences. No other sections (no "Try it", "Next steps", background or test logs).
